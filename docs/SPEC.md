# ТЗ: Lanscape — проверка сети и единая панель инфраструктуры

> Продукт выпускается в **двух редакциях** с разными бинарниками:
> **Lanscape Mini** — минимальный дашборд сети, где важен каждый байт, и **Lanscape** (Full) —
> единая панель с сервисами, uptime и дашбордом. Общая часть — протокол тестов и модель сегментов.
> Раздел 0 описывает Mini полностью и самостоятельно. Разделы 1–20 описывают Full.

## 0. Lanscape Mini

### 0.1. Назначение

Одна страница: **кнопка «Проверить всё» → матрица скоростей по каждой сети → простая
автоматическая карта**. Больше ничего. Агент должен без проблем помещаться на роутер с 16 МБ флеша
и 64 МБ RAM, а сервер — работать на том же роутере или на любой машине.

### 0.2. Состав

| Компонент | Что делает |
|---|---|
| `lsm-agent` | Сообщает интерфейсы (имя, IP/префикс, MAC, VLAN ID, скорость линка, состояние). Выполняет тесты по команде: ping/RTT/потери, PMTU с DF, TCP throughput A↔B с привязкой к интерфейсу |
| `lsm-server` | Держит список агентов, строит сегменты по подсети и VLAN, запускает прогон «все пути × все общие сегменты» серийно, отдаёт веб-страницу и JSON |

### 0.3. Функционал (исчерпывающий список)

1. Регистрация агента по общему токену. Агент сам подключается к серверу: исходящее TCP-соединение
   с переподключением.
2. Инвентаризация интерфейсов. Исключение интерфейсов по маске в конфиге (например, `wan*`, `tailscale*`).
3. Тесты на каждый путь: reachability, RTT (10 пакетов), PMTU 1500 (и jumbo, если MTU > 1500),
   TCP throughput в обе стороны (1 и 4 потока, 5 с).
4. Привязка к интерфейсу (`SO_BINDTODEVICE`) и сверка счётчика интерфейса до и после теста.
   Если трафик ушёл не туда, результат помечается «путь не совпадает».
5. Ожидаемая скорость:
   - по скорости линка;
   - для «неизвестной» (virtio) — ручное значение в конфиге сервера;
   - вердикт 🟢 / 🟡 / 🔴 / 🟣 (последний — CPU-bound по загрузке CPU агента во время теста).
6. Веб-страница:
   - кнопка «Проверить всё» и прогресс;
   - матрица по вкладкам сегментов;
   - карта, где сегменты — шины, узлы — карточки с портами, цвет по вердикту;
   - краткий список проблем: TCP ✗ при ICMP ✓, MTU ✗, скорость ниже ожидаемой, путь не совпадает.
7. Хранится только последний прогон и N предыдущих (по умолчанию 20) в одном JSON-файле.
   БД нет.
8. Выход наружу — только `GET /api/last` (JSON) и опциональный webhook по завершении прогона.

**Не входит в Mini**: обнаружение сервисов, uptime, дашборд плиток, пользователи и роли, OIDC,
история-графики, уведомления (кроме webhook), UDP-тесты, Aggregate, модули гипервизора/k8s/OpenWrt API,
LuCI-приложение (только init-скрипт и UCI-конфиг), IPv6-тесты (опционально позже).

### 0.4. Бюджет размера и ресурсов

| Цель | Бюджет |
|---|---|
| `lsm-agent`, linux/mipsle softfloat, статический, без сжатия | **≤ 128 КБ** (цель), жёсткий потолок 256 КБ |
| `lsm-agent`, linux/amd64, arm64 | ≤ 128 КБ |
| `lsm-server` вместе со встроенной страницей | ≤ 512 КБ (цель), потолок 1 МБ |
| Веб-страница (HTML + CSS + JS + SVG, gzip) | ≤ 40 КБ, без фреймворков и внешних CDN |
| RAM агента в простое / во время теста | ≤ 1 МБ / ≤ 4 МБ (плюс буферы сокетов) |
| RAM сервера на 20 агентов | ≤ 8 МБ |
| Пакет OpenWrt (`.ipk` / `.apk`) | ≤ 64 КБ в сжатом виде |

### 0.5. Технические решения ради размера

- **Язык**: C (musl, `-Os`, `-ffunction-sections -fdata-sections`, `--gc-sections`, `strip`) или
  Zig с `ReleaseSmall`. Go в Mini **не используется**: минимальный статический бинарник
  на Go — мегабайты. Rust допустим только с `panic=abort`, `opt-level="z"`, LTO, без std-тяжестей,
  и только если укладывается в бюджет.
- **Без сторонних библиотек.** Сеть — сырые сокеты POSIX. Интерфейсы — `getifaddrs` + `ioctl`
  (`SIOCETHTOOL` для скорости). VLAN ID берётся из `/proc/net/vlan/config`. Цикл событий — один
  `poll()`.
- **Протокол управления**: компактный бинарный (TLV) или строки `key=value` поверх TCP.
  Аутентификация — HMAC-SHA256 от токена по challenge. SHA-256 и HMAC реализованы у себя
  (~2 КБ кода). **TLS в Mini не встраивается**: доверенная LAN или внешний туннель /
  reverse-proxy. Это явно указано в документации.
- **JSON** на сервере формируется вручную (сериализатор без парсера). Сервер принимает только
  собственный протокол.
- **HTTP** на сервере минимальный: GET статики и API, POST `/api/run`, SSE для прогресса.
- **Страница**: один `index.html`, встроенный в бинарник в gzip и отдаваемый как есть
  (`Content-Encoding: gzip`). Карта рисуется SVG вручную: слои «сегменты сверху, узлы снизу»,
  без библиотек раскладки.
- **Тестовый трафик**: `send()` из заранее заполненного буфера (опционально `sendfile` из `/dev/zero`)
  и `recv()` в буфер, который сразу отбрасывается. Никаких аллокаций в горячем цикле.
- **Сборка**: один `Makefile` + кросс-тулчейны (`zig cc` удобен как универсальный кросс-компилятор).
  Цели:
  - `linux/{amd64,386,arm64,arm/v7,arm/v6,arm/v5,mips,mipsle,mips64,mips64le,riscv64,ppc64le}`;
  - `freebsd/amd64`;
  - пакеты OpenWrt через SDK.
- **CI-контроль размера**: сборка падает, если бинарник превысил бюджет. Размер по каждой
  архитектуре публикуется в релизе.

### 0.6. Установка Mini

- **OpenWrt**: пакет `lsm-agent` (и опционально `lsm-server`), procd init, конфиг в
  `/etc/config/lsm`.
- **Linux**: один бинарник + systemd-юнит или OpenRC-скрипт.
- **Docker**: образ `FROM scratch` с одним бинарником (размер образа ≈ размер бинарника),
  `network_mode: host`.
- **Kubernetes**: DaemonSet `hostNetwork: true` (манифест в репозитории, без Helm).

### 0.7. Совместимость с Full

- Протокол тестов (data-plane) у Mini и Full **общий и версионированный**.
- Сервер Full **принимает Mini-агентов** как «лёгкие узлы»: только сеть, без обнаружения
  и мониторов. Так роутеры и слабые устройства можно оставить на Mini-агенте в полной инсталляции.
- Mini-сервер Full-агентов не поддерживает. Миграция Mini → Full — смена сервера; агенты
  переподключаются.

### 0.8. Приёмка Mini

- Эталонная сеть из §20: один прогон «Проверить всё» даёт матрицу по 4 сегментам и карту.
- Регрессии «TCP перехвачен прокси», «macvlan-родитель», «MTU» распознаются.
- Размеры бинарников по всем целям укладываются в бюджет §0.4, что проверяется в CI.
- Агент на AX3000T занимает ≤ 1 МБ RAM в простое. Результат теста помечается 🟣, если упёрся в CPU.

# Lanscape (Full)

## 1. Цель

Одно место, куда заходишь и видишь состояние всей своей инфраструктуры: от кабелей и VLAN
до отдельных веб-сервисов. Продукт решает четыре задачи.

1. **Сеть**:
   - кнопка **«Проверить всё»** меряет пропускную способность, задержку, потери и MTU по каждому пути;
   - путь — это пара узлов × общая сеть. Меряются все интерфейсы разной скорости, а не только основной;
   - результат сравнивается с ожидаемым, и видно, где просадка.
2. **Карта**: автоматически построенная схема устройств, интерфейсов, сегментов (подсеть/VLAN)
   и запущенных на них сервисов, окрашенная по состоянию.
3. **Сервисы и доступность**:
   - **автообнаружение** всего, что запущено: контейнеры, ВМ, поды, веб-интерфейсы, порты;
   - добавление найденного в мониторинг uptime одним кликом;
   - история, инциденты, уведомления, страница статуса.
4. **Дашборд**: стартовая страница с плитками сервисов (иконки, группы, поиск), виджетами состояния
   и ссылками, которые сами выбирают внутренний или внешний адрес.

Агент ставится на что угодно: Linux-хост, гипервизор, ВМ, контейнер, Docker/Compose (NAS),
Kubernetes, роутер OpenWrt (с интерфейсом в LuCI), macOS, Windows, FreeBSD.

## 2. Термины

| Термин | Значение |
|---|---|
| **Сервер (control plane)** | Центральный сервис: веб-панель, API, планировщик, хранилище |
| **Агент** | Процесс на узле: инвентаризация, тесты сети, обнаружение сервисов, проверки доступности |
| **Узел** | Устройство или окружение с агентом (хост, ВМ, контейнер, под, роутер, NAS) |
| **Устройство без агента** | Найдено сканированием, DHCP/ARP, mDNS и т.п.: принтер, камера, ТВ, коммутатор |
| **Сегмент** | L2/L3-сеть: подсеть и VLAN, если известен |
| **Путь** | Направленная пара «интерфейс узла A → адрес узла B» в сегменте |
| **Сервис** | Что-то, к чему можно подключиться: URL, `host:port`, DNS-имя, контейнер, workload |
| **Монитор** | Правило периодической проверки сервиса (HTTP, TCP, ping, DNS, TLS, heartbeat…) |
| **Точка наблюдения** | Агент, с которого выполняется монитор. Их может быть несколько |
| **Прогон** | Один запуск набора тестов сети |

## 3. Архитектура

```
             ┌─────────────────────────────── Сервер ────────────────────────────────┐
 браузер ──► │ Web UI (SPA) · REST/WS API · планировщик · БД · уведомления · /metrics │
             │ модули: Сеть · Карта · Обнаружение · Uptime · Дашборд · Инвентарь      │
             └──────────────▲─────────────────────────────────▲──────────────────────┘
                            │ управление: исходящее WSS (mTLS)│
            ┌───────────────┴──────┐              ┌───────────┴────────────┐
            │ Агент A              │◄────────────►│ Агент B                │
            │ тесты · обнаружение  │ тест. трафик │ проверки доступности   │
            └──────────────────────┘              └────────────────────────┘
```

- **Управляющий канал** всегда исходящий от агента (WebSocket over TLS или gRPC).
  Агенту за NAT не нужны входящие порты для управления.
- **Тестовый трафик** идёт напрямую между агентами. Проверки доступности выполняют агенты
  (точки наблюдения) или сам сервер.
- Сервер `lanscape` — один статический бинарник (рекомендуется Go) со встроенным SPA.
  БД — SQLite по умолчанию, PostgreSQL опционально. Временные ряды хранятся в самой БД
  с даунсэмплингом, экспорт в Prometheus.
- Агент `lanscape-agent` — один статический бинарник (`CGO_ENABLED=0`) со встроенным движком тестов и проверок.
  Внешние `iperf3`, `ping` и `nmap` не требуются.
- Сервер можно запустить и без агентов: тогда он работает как дашборд и uptime-монитор со своей
  точки наблюдения.

## 4. Регистрация и безопасность

- Агент регистрируется по одноразовому или многоразовому **токену** из панели (метки, срок действия),
  затем работает по **mTLS** с автоматической ротацией сертификатов.
- Тестовые соединения между агентами аутентифицируются токеном прогона. Агента нельзя использовать
  как генератор трафика извне.
- Панель:
  - локальные пользователи, OIDC, 2FA (TOTP), API-токены;
  - роли: «просмотр», «оператор» (запуск тестов, подтверждение инцидентов), «администратор»;
  - гостевой режим только для дашборда и страницы статуса.
- Секреты мониторов (Basic-auth, заголовки, токены API) хранятся зашифрованными и в UI маскируются.
- Ограничения на агенте:
  - максимальная скорость и длительность теста;
  - запрещённые интерфейсы (`wan`, `tailscale0`…);
  - **запрет активного сканирования** — по умолчанию выключено, включается явно по подсетям;
  - режимы «только проверки» и «только отвечать».
- Порт данных для тестов поднимается только на время теста либо используется один фиксированный
  порт с аутентификацией.

## 5. Инвентаризация

Агент при старте, по изменениям netlink и периодически (по умолчанию раз в 5 минут) сообщает:

1. **Интерфейсы**:
   - имя, MAC, MTU, состояние, IPv4/IPv6;
   - тип: physical, bridge, bond, vlan, macvlan, veth, wireguard, tun…;
   - родитель, VLAN ID, члены bridge/bond, режим bond;
   - **скорость линка** (ethtool). Если драйвер её не сообщает (`virtio` → `-1`), значение
     помечается «неизвестно» (см. §7.4).
2. **Маршрутизация**: таблицы, `ip rule`, шлюзы, policy routing.
3. **Соседи**: ARP/NDP, LLDP/CDP (если доступны).
4. **Окружение**:
   - bare-metal / VM / LXC / Docker / Kubernetes pod / OpenWrt;
   - гипервизор-родитель (модуль гипервизора сообщает гостей и их MAC);
   - k8s-нода, CNI.
5. **Ресурсы**: архитектура, CPU, RAM, **диски** (заполненность, SMART, если доступен), аптайм,
   версия ОС и ядра, **наличие обновлений** пакетов.

Сервер:

- группирует интерфейсы в **сегменты**;
- ведёт **IPAM**: занятые и свободные адреса по сегментам, пересечение с DHCP-пулами;
- выявляет аномалии:
  - дубли IP и MAC;
  - VIP сразу на двух узлах;
  - одна подсеть на разных VLAN;
  - интерфейс без линка;
  - новый неизвестный MAC в сети.

## 6. Тесты сети

### 6.1. Виды

| Тест | Что меряет | По умолчанию |
|---|---|---|
| Reachability | ICMP и TCP-connect до адреса узла в сегменте | 3 пакета |
| Latency | RTT min/avg/p95/max, jitter, потери | 20 пакетов, 50 мс |
| **MTU / PMTU** | Проходит ли кадр полного размера с DF (1500 / jumbo) | — |
| **Throughput TCP** | A→B и B→A, 1 и N потоков | 5 с на направление, N=4 |
| Throughput UDP | Скорость, потери, jitter на заданной полосе | опционально |
| Bidirectional | Одновременно в обе стороны | опционально |
| Aggregate | Все пары сразу: суммарная ёмкость, узкие аплинки | вручную |
| Internet | Выход наружу, публичный IP и скорость до внешнего сервера через каждый шлюз | опционально |

### 6.2. Привязка к интерфейсу (ключевое требование)

- Сокет привязывается к адресу и к устройству (`SO_BINDTODEVICE` / `IP_BOUND_IF`).
- До теста агент по таблицам и `ip rule` проверяет, что трафик пойдёт через нужный интерфейс.
  Если нет — результат «путь не совпадает с ожидаемым», а не ложная цифра.
- После теста агент сверяет, что вырос счётчик именно этого интерфейса.
- Известные ловушки распознаются и объясняются в отчёте:
  - **macvlan**: родитель не видит своих детей, нужен macvlan-«брат»;
  - прозрачные прокси (TPROXY/REDIRECT) в новых подсетях. Симптом: ICMP ✓, TCP ✗;
  - асимметрия маршрутов и rp_filter;
  - policy routing.

### 6.3. Планирование

- **Серийно** (по умолчанию): не больше одного throughput-теста на физическом аплинке одновременно.
  Учитываются гости одного гипервизора и узлы за одним коммутатором.
- **Параллельно**: для Reachability и Aggregate.
- Оценка времени прогона заранее, отмена, сохранение частичных результатов.
- Расписания: например ночной полный прогон и лёгкий Reachability каждые 5 минут.

### 6.4. Ожидаемые значения и вердикт

- Ожидаемая скорость берётся как минимальная из скоростей линков на пути либо задаётся вручную.
- Вердикт:
  - 🟢 ≥ 85% ожидаемого;
  - 🟡 50–85%;
  - 🔴 < 50% или ошибка;
  - ⚪ нет данных;
  - 🟣 ограничено CPU агента (роутер, слабый NAS).
- Отдельные вердикты для MTU, потерь больше 0.5% и RTT выше порога.

## 7. Карта

### 7.1. Построение (автоматически)

- **Устройства** — карточки с иконкой по типу (роутер, NAS, гипервизор, VM, LXC, k8s-нода, под,
  ПК, телефон, принтер, камера, ТВ, точка доступа). Устройства без агента берутся из обнаружения (§8).
- **Интерфейсы** — порты на карточке: имя, IP, скорость.
- **Сегменты** — узлы-«шины» (подсеть · VLAN · ожидаемая скорость).
- **Вложенность**: гости внутри гипервизора, поды внутри ноды. Сворачивается.
- **Сервисы** — значки на устройстве: иконка приложения и статус uptime. Можно скрыть.
- **Рёбра путей** — цвет по вердикту, подпись со скоростью.
- **Неуправляемые коммутаторы и аплинки** выводятся из данных: если суммарный потолок между
  группами узлов ниже скорости их портов, появляется гипотеза «узкое место X Гбит/с».
  Её можно подтвердить и оформить на карте как коммутатор.
- **Внешние зависимости**: интернет, провайдер, облачные узлы и VPN-пиры — отдельной зоной.

### 7.2. Интерактивность

- Авто-раскладка (ELK / dagre / силовая). Ручные позиции сохраняются.
- Слои: физика и сегменты / сервисы / пути. Фильтры: «только проблемы», по сегменту, по группе.
- Клик по элементу открывает карточку: история, метрики, связанные сервисы, «перемерить»,
  «открыть веб-интерфейс».
- Экспорт в PNG/SVG, ссылка на состояние карты. Режим «на стену»: полноэкранный, автообновление.

### 7.3. Матрица

Таблица «узел × узел» по каждому сегменту: скорость в обе стороны, цвет вердикта.

### 7.4. Неизвестная скорость линка

Три правила по порядку:

1. ручное значение;
2. наследование от физического аплинка моста гипервизора;
3. «неизвестно»: вердикт по скорости не ставится, показывается только абсолютное значение.

## 8. Автообнаружение сервисов и устройств

### 8.1. Источники

Каждый источник включается отдельно. Найденное попадает в очередь **«Найдено»**, а не сразу
в мониторинг.

| Источник | Что даёт |
|---|---|
| **Слушающие сокеты на узле** (агент, `ss`/`netstat`) | Порт, протокол, процесс, пользователь. Без сканирования сети |
| **Docker / Compose** (сокет Docker) | Контейнеры, образы, опубликованные порты, compose-проект, labels, healthcheck, состояние |
| **Kubernetes** (API, read-only) | Service (включая LoadBalancer IP), Ingress / Gateway API (хосты, TLS), Deployment / StatefulSet / DaemonSet и их готовность, PVC |
| **Гипервизор** (Proxmox API / `qm`, `pct`; libvirt) | VM и CT, их статус, IP (guest agent), теги и заметки |
| **OpenWrt** (ubus / UCI) | DHCP-аренды и hostname, статические аренды, Wi-Fi-клиенты, port forwarding, SQM |
| **mDNS / DNS-SD, SSDP/UPnP, NetBIOS/LLMNR** | Принтеры, AirPlay/Chromecast, NAS, медиа-серверы, IoT |
| **ARP/NDP и таблицы соседей** | Устройства без агента, вендор по MAC (OUI) |
| **Активное сканирование** (явно по подсетям, мягкий rate-limit) | Открытые TCP-порты из списка популярных, баннеры |
| **Reverse proxy** (Traefik API, Caddy admin API, конфиги nginx) | Публикуемые имена и бэкенды |
| **DNS-серверы** (API Technitium / Pi-hole / AdGuard; AXFR, если разрешён) | Имена в локальной зоне и их адреса |
| **TLS-сертификаты** | SAN-имена и срок действия — для привязки имён и мониторинга истечения |
| **Prometheus** (targets API), **Home Assistant**, **Uptime Kuma** (импорт) | Уже известные цели |

### 8.2. Распознавание приложений

- HTTP-фингерпринт по `<title>`, favicon (хэш), заголовкам, характерным путям и JSON-ответам.
  Библиотека сигнатур 300+ популярных self-hosted приложений (Grafana, Jellyfin, Home Assistant,
  Gitea, Vaultwarden, Proxmox, OpenWrt LuCI, Synology DSM, Longhorn, Argo CD, Nextcloud, Immich
  и т.д.) — это иконка, категория и рекомендуемый монитор.
- Для контейнеров и workload'ов — по образу (`vaultwarden/server` → Vaultwarden).
- Сигнатуры обновляются отдельно от релизов. Пользователь может добавлять свои.

### 8.3. Слияние и жизненный цикл

- Один сервис, найденный разными путями, склеивается в одну карточку. Например, Ingress
  `git.example` + Service + Deployment + HTTP-ответ Gitea = «Gitea» со всеми адресами:
  внутренний URL, внешний URL, `host:port`, workload.
- Статусы найденного: **новое** → добавлено / игнорируется (правило) / скрыто.
- Правила авто-добавления: например «все Ingress с TLS → монитор HTTPS + плитка на дашборде».
- **Лента изменений**:
  - появился новый сервис или устройство;
  - открылся или закрылся порт;
  - сменился IP;
  - контейнер пропал;
  - новый MAC в сети.

## 9. Мониторинг доступности (uptime)

### 9.1. Типы мониторов

| Тип | Проверка |
|---|---|
| HTTP(S) | Код, время ответа, ключевое слово или regex, JSON-путь, редиректы, заголовки, basic/bearer |
| TCP / UDP | Подключение к порту, ответ на отправленные байты (опционально) |
| ICMP | Доступность и RTT |
| DNS | Резолв записи через заданный сервер, ожидаемое значение |
| TLS | Срок действия сертификата (предупреждение за N дней), цепочка, имя |
| Контейнер | Состояние и healthcheck Docker |
| Kubernetes | Готовность workload, рестарты подов, Pending, статус PVC |
| VM / CT | Запущен ли гость на гипервизоре |
| Heartbeat (push) | Внешний процесс раз в N минут дёргает URL (cron, бэкапы, скрипты). Нет сигнала — инцидент |
| Интерфейс/путь | Привязка к вердикту сети из §6 |
| Домен | Срок регистрации домена (WHOIS/RDAP) |
| Составной | «Сервис жив, если A и (B или C)» |

### 9.2. Точки наблюдения

- Монитор может выполняться с нескольких агентов: из разных сегментов, снаружи через облачный
  агент или VPN. Условие инцидента — «недоступен с ≥ N точек».
- Это разделяет «упал сервис» и «упал путь до него». Отчёт показывает: «Gitea доступна из LAN,
  недоступна из VLAN 100 → проблема маршрутизации или файрвола».
- **Зависимости**: если лёг роутер или гипервизор, дочерние инциденты подавляются и группируются
  («32 сервиса недоступны, причина — prx1 offline»). Граф зависимостей строится из карты
  и уточняется вручную.

### 9.3. Инциденты и уведомления

- Инцидент открывается после N подряд неудачных проверок. Есть подтверждение и комментарии,
  закрытие происходит автоматически.
- Окна обслуживания: плановые и «прямо сейчас на 30 минут». В окне уведомления не шлются,
  а в статистике время отмечается отдельно.
- Каналы уведомлений:
  - Telegram, email, webhook, ntfy, Gotify;
  - Discord/Slack/Matrix;
  - push в PWA.
- Дедупликация, эскалация и тихие часы.
- **Uptime %** за день, неделю, месяц и год; графики времени ответа; SLA-цели на сервис.

### 9.4. Страница статуса

Публичная или по ссылке. Группы сервисов, история 90 дней, текущие инциденты и плановые работы.
Кастомный домен и тема.

## 10. Дашборд (стартовая страница)

- **Плитки сервисов**: иконка, имя, статус (точка uptime), время ответа, короткая метрика
  (например, свободное место у NAS). Группы, сортировка, перетаскивание.
- **Умные ссылки**: у сервиса есть внутренний и внешний адрес. Панель сама открывает нужный
  в зависимости от того, откуда зашёл пользователь (из локальной сети или снаружи).
- **Поиск и командная палитра** (`Ctrl/⌘+K`): поиск по сервисам, устройствам, IP и MAC.
  Действия прямо оттуда: «открыть», «перемерить сеть до…», «Wake-on-LAN».
- **Виджеты**:
  - общий статус: зелёных, жёлтых, красных, открытые инциденты;
  - ресурсы узлов: CPU, RAM, диск, температура; топ по заполненности дисков;
  - сеть: последний прогон, карта в миниатюре, текущий трафик WAN/LAN (с роутера), скорость
    интернета по расписанию, история падений провайдера;
  - хранилище: пулы и диски, SMART-предупреждения, свободное место;
  - бэкапы: последний успешный по каждому источнику (heartbeat или интеграция), «давно не было»;
  - сертификаты и домены: что скоро истекает;
  - обновления: доступные обновления ОС и пакетов на узлах, новые теги образов контейнеров;
  - лента изменений (§8.3);
  - ИБП (NUT): заряд, нагрузка, время на батарее;
  - энергопотребление (умные розетки, IPMI), если подключены;
  - заметки и ссылки (runbook, документация).
- Несколько дашбордов (например «Главный», «Медиа», «Инфраструктура»), видимость по ролям.
- PWA: добавление на рабочий стол телефона, офлайн-кеш последнего состояния.

## 11. Действия (опционально, с подтверждением и аудитом)

- Wake-on-LAN для устройств с известным MAC.
- Перезапуск контейнера, workload'а, VM/CT — через соответствующий API и только для ролей
  с правом «оператор».
- Повторить тест сети или проверку.
- Все действия пишутся в журнал аудита: кто, что, когда, результат.

### 13.1. Архитектуры

`linux/amd64`, `386`, `arm64`, `arm/v7`, `arm/v6`, `arm/v5`, `mips`/`mipsle` (softfloat),
`mips64`/`mips64le`, `riscv64`, `ppc64le`, `s390x`; `darwin/amd64`, `darwin/arm64`;
`windows/amd64`, `windows/arm64`; `freebsd/amd64`, `freebsd/arm64`.

- Статическая сборка.
- Docker — multi-arch manifest.
- Релизы с контрольными суммами и подписью (cosign/minisign).
- Автообновление агента из панели (с каналами stable/beta).

### 13.2. LuCI (`luci-app-lanscape`)

- Статус подключения, токен, адрес сервера.
- Выбор интерфейсов для тестов: `wan` по умолчанию исключён.
- Лимиты скорости и длительности.
- Галочки источников обнаружения: DHCP-аренды, Wi-Fi-клиенты, port forwarding.
- Кнопка «Проверить с этого роутера», последние результаты.
- Backend на `rpcd`/`ucode`, конфиг в UCI (`/etc/config/lanscape`).
- Тест, упёршийся в CPU роутера, помечается 🟣.

## 14. Движок агента

- **Сеть**:
  - TCP (N потоков, прогрев 1 с не учитывается) и UDP (полоса, потери, jitter);
  - ICMP через raw или unprivileged сокет с fallback на TCP-ping;
  - PMTU;
  - монотонные таймеры, отчёт о CPU агента;
  - опционально — клиент, совместимый с `iperf3 -s`.
- **Проверки**: HTTP-клиент (HTTP/1.1, HTTP/2, TLS с проверкой цепочки), DNS-клиент (UDP/TCP/DoT/DoH),
  TCP/UDP-пробы, ICMP.
- **Обнаружение**: сокеты, Docker, k8s, гипервизор, ubus, mDNS/SSDP, ARP, rate-limited
  сканер портов, HTTP-фингерпринт.
- Нагрузка ограничивается конфигом: частота проверок, параллелизм, лимит на сканирование.

## 15. API и интеграции

- REST + WebSocket, OpenAPI.
- **Prometheus** `/metrics`: пути, мониторы, агенты, устройства. Готовые дашборды Grafana.
- **GitOps**: сервисы, мониторы, сегменты, дашборды и правила описываются в YAML, есть импорт и экспорт.
- Импорт из Uptime Kuma, Homepage/Homer/Dashy (плитки), Prometheus targets.
- Webhook по событиям: прогон завершён, инцидент, новое устройство.
- Опционально — объекты Home Assistant (состояние сервисов и устройств как сенсоры).

## 16. Нефункциональные требования

| Требование | Значение |
|---|---|
| Агент в простое | < 15 МБ RAM, ~0% CPU, трафик управления < 1 КБ/с |
| Сервер | < 250 МБ RAM на 100 агентов и 500 мониторов; SQLite по умолчанию |
| Полный прогон сети | 4 узла × 4 сегмента ≤ 5 мин; 10 узлов × 3 сегмента ≤ 15 мин (серийно) |
| Погрешность throughput | ±5% относительно `iperf3` на том же пути |
| Мониторы | Минимальный интервал 10 с; 500 мониторов на один сервер без деградации |
| Обнаружение | Первичный отчёт ≤ 2 мин после подключения агента; активное сканирование не быстрее заданного rate-limit |
| Хранение | Сырые данные 30 дней, агрегаты 2 года (настраивается) |
| Доступность | Переподключение агентов с backoff. Сервер переживает рестарты. Бэкап и восстановление БД одной командой |
| Совместимость | Linux kernel ≥ 4.x; OpenWrt ≥ 23.05 |
| Лицензия | MIT или Apache-2.0 |

## 18. Критерии приёмки (общие)

- «Проверить всё» из панели запускает полный прогон без SSH. По окончании видны матрица по
  сегментам, карта и список проблем.
- Узел с несколькими интерфейсами в разных сегментах: каждый путь измерен отдельно, трафик
  подтверждённо шёл через заявленный интерфейс.
- Искусственно созданные проблемы находятся и объясняются:
  - выключенный VLAN;
  - перехват TCP прокси;
  - уменьшенный MTU;
  - порт 100M вместо 1G.
- После подключения агентов к k8s, Docker и гипервизору в очереди «Найдено» появляются
  веб-сервисы с правильными иконками. Одним кликом они добавляются в мониторинг и на дашборд.
- Остановка контейнера или workload'а даёт инцидент и уведомление в течение 2 интервалов проверки.
  Падение гипервизора даёт один сгруппированный инцидент, а не десятки.
- Агент ставится на OpenWrt из пакета и настраивается в LuCI, на NAS — через `docker compose up -d`,
  в k8s — через `helm install`.

## 19. Идеи на будущее

- **Карта Wi-Fi**: клиенты по точкам доступа, уровень сигнала и скорость согласования, «слабые» клиенты.
- **Анализ трафика**: топ-разговоров по NetFlow/sFlow/conntrack с роутера. Кто забил канал
  в конкретный момент.
- **Проверка изоляции**: матрица «кто кого должен и не должен видеть» между сегментами (IoT-VLAN
  не должен достучаться до NAS). Регулярный автотест правил файрвола.
- **Снимки конфигураций**: периодическое сохранение конфигов роутера, коммутаторов и гипервизоров,
  diff изменений в ленте.
- **Документация из данных**: автогенерация страницы «как устроена сеть» (сегменты, адреса, сервисы)
  в Markdown/PDF.
- **Планировщик IP**: подсказка свободного адреса и VLAN при добавлении устройства, проверка
  конфликтов до применения.
- **Сценарии «что если»**: на карте выключить узел или линк и увидеть, какие сервисы пострадают
  (по графу зависимостей).
- **Внешний взгляд**: облачный агент проверяет публичные адреса, открытые наружу порты,
  DNS-записи и сертификаты.
- **Энергия и тишина**: расписания выключения и WoL для редко нужных машин, учёт потребления.
- **Мобильное приложение / виджеты ОС** со статусом и push-уведомлениями.
- **Плагины**: SDK для своих источников обнаружения, мониторов и виджетов.

### 20.3. Ожидаемые результаты

- **Сеть**:
  - VLAN 300 ≈ 2.0–2.4 Гбит/с 🟢 (базовый замер iperf3 ≈ 2.0–2.1);
  - VLAN 301 ≈ 0.9 Гбит/с 🟢;
  - pod network (Cilium vxlan) ≥ 70% от VLAN 300.
- **Обнаружение** находит:
  - все Ingress кластера с иконками приложений (Gitea, Vaultwarden, Longhorn, Argo CD, Navidrome…);
  - LoadBalancer-сервисы на 192.168.1.195–210 и 192.168.0.195;
  - LXC и VM Proxmox;
  - NFS на NAS;
  - DNS-сервер 192.168.1.11;
  - веб-интерфейсы роутера и Proxmox.
- **Мониторы по умолчанию** после одного клика:
  - HTTPS всех Ingress;
  - TCP 6443 на VIP;
  - DNS через 192.168.1.11;
  - NFS 2049;
  - TLS-сроки сертификатов;
  - heartbeat бэкапов Longhorn (дважды в неделю).
- **Регрессии, которые система должна поймать и объяснить** (реально встречались):
  - TCP в 10.30/10.31 перехватывается прозрачным прокси: ICMP 🟢, TCP 🔴;
  - хост не достаёт до macvlan-подов на родительском интерфейсе → рекомендация macvlan-брата;
  - VIP 192.168.1.199 одновременно на двух узлах;
  - корень гипервизора заполнен на 100% → виджет «диски» 🔴 и связанный инцидент по ВМ,
    чей диск лежит на этом разделе.
